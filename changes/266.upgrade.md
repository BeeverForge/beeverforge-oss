**An OpenFactory 0.7 add-on still loads, until 1.1.** Rows a package declares under `openfactory.adapters`, 0.7's entry-point group, are read after `beeverforge.adapters`'s, so a 0.7 add-on's kinds keep working after an upgrade in place. A name declared in both groups is the `beeverforge.adapters` row, and the platform's own rows still win over either. One warning names each package still on the old group: move its entry points to `beeverforge.adapters`, because BeeverForge 1.1 stops reading `openfactory.adapters`.

**Re-running the installer with `--force` over an OpenFactory 0.7 compose deployment upgrades it in place, with its data.** When the directory's `.env.compose` holds `OPENFACTORY_*` rows, the installer runs `beeverforge upgrade-from-openfactory` before rewriting the file. It stops the 0.7 stack's containers without removing them, and copies its Temporal database, state, repository cache and journals into the volumes BeeverForge's compose uses. Before, the upgraded stack started on empty volumes, with no card in flight and no project registered. The harness toolbox is not copied: the new image fills it again with its own harness CLI. 0.7's volumes are left as they were, so going back is starting 0.7 again; once BeeverForge runs as it should, the installer's last lines name the `docker rm` and `docker volume rm` commands that remove them. If the upgrade stops after 0.7's containers were stopped, the installer says how to start them again. A volume a BeeverForge stack already keeps data in is never written over: the installer stops and names it.

**`init --force` carries a 0.7 `.env.compose`'s `OPENFACTORY_*` rows as their `BEEVERFORGE_*` names**, so the credentials, tokens and settings reach the rows compose reads, and a `BEEVERFORGE_*` value the file already holds wins. The installer also keeps the work directory 0.7's file names in `OPENFACTORY_WORK_DIR`.

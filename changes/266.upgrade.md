**Re-running the installer with `--force` over an OpenFactory 0.7 compose deployment upgrades it in place, with its data.** When the directory's `.env.compose` holds `OPENFACTORY_*` rows, the installer runs `beeverforge upgrade-from-openfactory` before rewriting the file. It stops the 0.7 stack's containers without removing them, and copies its Temporal database, state, repository cache and journals into the volumes BeeverForge's compose uses. Before, the upgraded stack started on empty volumes, with no card in flight and no project registered. The harness toolbox is not copied: the new image fills it again with its own harness CLI. 0.7's volumes are left as they were, so going back is starting 0.7 again; remove them with `docker compose -p openfactory down -v` once BeeverForge runs as it should. A volume a BeeverForge stack already keeps data in is never written over: the installer stops and names it.
**`init --force` carries a 0.7 `.env.compose`'s `OPENFACTORY_*` rows as their `BEEVERFORGE_*` names**, so the credentials, tokens and settings reach the rows compose reads, and a `BEEVERFORGE_*` value the file already holds wins. The installer also keeps the work directory 0.7's file names in `OPENFACTORY_WORK_DIR`.

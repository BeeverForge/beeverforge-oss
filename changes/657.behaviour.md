**The engine connection presents a client certificate and an API key together, pins the engine's own CA, and reads a stored key again without reconnecting.** With `TEMPORAL_API_KEY`, `TEMPORAL_TLS_CERT` and `TEMPORAL_TLS_KEY` all set, the worker and the panel present the certificate and send the key as the bearer token, which a self-hosted Temporal server with mutual TLS and a JWT authorizer both on asks for; before, the key replaced the certificate and such a server refused the connection at the handshake. Either alone behaves as before. `TEMPORAL_TLS_SERVER_CA_CERT` names the CA the engine's server certificate is checked against, for the engine connection alone, without changing the trust store the rest of the process uses. The key is read again from where it is stored every `TEMPORAL_AUTH_REFRESH_SECONDS` (60 unset) and on each connect, and a key that changed is handed to the client already held, so a short-lived token rotated in place keeps the worker polling with no reconnect and no restart; a re-read that is refused or answers nothing keeps the key the client has and says so by name, never by value.

**An OpenFactory 0.7 deployment upgraded in place keeps its Temporal work, and stops running 0.7's schedules.** Until 1.0, the worker also polls 0.7's task queue `openfactory-jobs` with the same workflows and activities, so a job, a merge gate or a deploy watch that 0.7 started before the upgrade is picked up rather than stranded; nothing new is started there. Such a workflow keeps 0.7's id (`openfactory-<project>-<issue>`, `openfactory-coordinator-<project>`), and the panel, its engine link, the gates, the tech-lead's rounds and the floor read it under that id, while a running 0.7 coordinator is sent decisions rather than doubled, and a requirement whose 0.7 breakdown still runs is read as being broken down and is not broken down a second time beside it; a running 0.7 job holds the floor like any other, which is what keeps a card from being started twice. If either queue's worker stops, the other stops with it. Picked up is not proven to replay: a workflow whose history this release's code no longer matches fails its workflow task in the worker's log, by name, without stopping the worker, so let 0.7's in-flight jobs finish before upgrading when you can. At boot, once BeeverForge's own schedules exist, it deletes 0.7's (`openfactory-poller`, `openfactory-preview-reaper` and each project's `openfactory-product-sweep-`, `openfactory-techlead-watch-`, `openfactory-card-questions-` and `openfactory-okf-refresh-` schedule), which would otherwise scan every board and report every sweep twice, and says in one log line which it deleted; one it cannot delete is logged as an error by name, and the next boot tries again. A poller paused in 0.7 is not carried over: `beeverforge-poller` starts running, so pause it again if the queue was held.

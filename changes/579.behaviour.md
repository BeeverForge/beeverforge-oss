**`onboard` is now a catalogue action, reachable through both transports with the catalogue's authorization and audit.** Through the API it starts the onboarding on the worker and answers the run's handle, and each repository's steps (read, manifest, proof, map, pull request) are journaled as they end. An unknown project, a source that is not a repository reference the project's forge can name, or a box the worker cannot prove in answers a reason and starts nothing. A repository a provider refuses is that repository's failed step, with the remedy, and the others still run. A second run finds what the first left and says that nothing changed. The CLI verb `beeverforge onboard` now calls the action, and two of its answers change on purpose: a malformed `--source` is refused before anything is cloned, with exit 2, and a product that has no code yet is refused, as every other action that needs code refuses it.

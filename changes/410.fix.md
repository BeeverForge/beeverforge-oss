**On Azure DevOps, a ref qualified with the wrong project, such as `Owner/api` for an adapter of `api` in project `Desk`, is read where it is cloned again.** The forge cloned it from `Desk`, because the qualifier of the adapter's own repository is ignored, but it read the API for it (branches, pull requests, branch policies) in `Owner`, a project that does not exist. Both now pick the project with one rule, so the clone and the reads go to `Desk`, and a ref naming the own repository in another case, such as `Docs/API`, is read in `Desk` too. A ref naming another repository, such as `Docs/web`, still uses the project it names for both. The forge's list of disabled pipelines also matched a pipeline's repository by spelling, so a pipeline of `API` was not counted as `api`'s; it now matches without case. The branch delete and the pull-request reads and writes (`merge_pr`, `pr_status`, the description and the diff) used the adapter's own project for every ref, so a documentation branch in `Docs/web` was cloned and listed in `Docs` but deleted from, merged in and read back in `Desk`: a landed documentation pull request could not be merged or read, and the delete could remove a `req/*` branch from a repository of the same name in `Desk`. They now pick the project with the same rule.

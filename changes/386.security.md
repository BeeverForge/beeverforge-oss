**The host's push no longer reads git configuration a job could write, and runs no git command in the job's repository.** A job can write the git configuration of the repository it works in (the worktree box's `.git/config` and `config.worktree`, or the container box's host clone, which the box sees as /workspace), and on the worktree box, where it runs as the worker's user, the user-level git config and ssh config too. The authenticated push to the forge used to run in the job's repository, so a URL rewrite (`url.<base>.insteadOf` or `pushInsteadOf`) could send the push, and its credential, somewhere other than the forge, and `core.sshCommand` could make the host run a program. Both boxes now push from a bare repository the host makes for each push, outside every mount: it borrows the job's objects (`objects/info/alternates`, objects only), takes the branch's commit from the job's ref read as data, and pushes with the forge's URL as an argument. With a forge URL the push reads no user-level, system or ssh configuration either, so a proxy or CA certificate set in a git config file no longer reaches it: set it in the environment (`HTTPS_PROXY`, `GIT_SSL_CAINFO`). With no forge URL, the push goes to the `origin` the repository had before the job ran and keeps the person's own git and ssh configuration, in the workload's own environment on the worktree box (`SECURITY.md`, credential reach). A branch whose ref is symbolic, a symlink or not an object name, a repository keeping its refs in a reftable, and a container clone whose `.git` the job replaced are refused, each saying what to do. The other host-side git calls that still run in a job's repository (the rebase onto a moved base, the local forge's merge) are tracked in a follow-up issue.

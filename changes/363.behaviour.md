**The worker image runs the worker and the panel in one container.** `beeverforge worker --with-panel` starts the durable worker and the panel against an engine run elsewhere, needing `TEMPORAL_ADDRESS`, `TEMPORAL_NAMESPACE` and `TEMPORAL_API_KEY` and a panel sign-in, and is a valid `CMD` for the published `beeverforge-worker` image under its `tini`. The panel shares the worker's environment and credentials in this mode, so the command refuses, by name, to serve an open panel off the loopback: on the default `0.0.0.0`, or any other non-loopback `--panel-host`, it starts only when the panel asks for a sign-in — `BEEVERFORGE_PANEL_TOKEN` or `BEEVERFORGE_PANEL_TOKENS`, or anything else that closes the panel, as single sign-on does; `--panel-host 127.0.0.1` keeps the panel on the loopback for a container that publishes no port, and starts without one. SIGTERM stops both, and when either process ends the command exits with that process's status, so a restart policy sees it. Its own lines follow `BEEVERFORGE_LOG_FORMAT`, as the worker's and the panel's do. `beeverforge up` now also exits with the status of the process that ended its set, where it exited 0 before. `docs/operations.md` shows the container command beside the compose stack's, with the variables to leave out of that container.

**Eleven more readers name a file that is not UTF-8 and the byte, instead of crashing.** A file saved as Latin-1 or UTF-16 raised a decoding error out of the loading of a project's manifest (`.beeverforge/project.yaml`), the proposal of a project's preview (its manifest), the recording of a decision, the acceptance, the drop and the supersession of a requirement, the product's facts pack (its `README.md`), the record of the product's knowledge refreshes, and the upgrade from an OpenFactory 0.7 compose stack (its `.env.compose`); a product's `template.yaml` was refused in the decoder's own words, naming neither the byte nor the remedy, and so was the manifest by `beeverforge explain`. Each now answers with one sentence naming the file, the byte offset where it stops being UTF-8 text and the remedy, save it as UTF-8, and writes nothing over the file: a manifest is refused as one that does not load, the proposal and the requirement writers refuse, a supersession counts the requirement as not retired, the facts pack adds nothing, leaving its README as it was, and says so, the knowledge status names the record, and the upgrade stops before anything is stopped or copied, so the installer keeps `.env.compose` as it was. UTF-16 without a byte-order mark is caught too, even when its text is all ASCII and so its bytes are valid UTF-8: at its first NUL byte.
